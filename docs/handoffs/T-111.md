# HANDOFF T-111
## Summary
Replaced the three placeholder modules with the Phase 1 core primitives. `clock` has the `Clock` trait, `SystemClock` (the
only reader of the OS clock) and `SimClock` (behind `cfg(any(test, feature = "sim"))`). `events` has `BackendEvent`
(the six contract event names, JSON snapshot payloads), the `EventSink` trait, `NullSink` and `RecordingSink`.
`limits` enforces the rule 1 ceilings in memory: session permits (RAII), a rolling 60-minute prompt window, turns per task
id, UTC-day run minutes, and the 30-minute idle / background presence rule, all read from `compliance::ceilings` with
`min(user, ceiling)` as the only combination. It exposes a `snapshot()` / `load()` pair for T-112 to persist.

## Open risks / questions
- `ProviderId` is defined here as `limits::ProviderId`. T-112 plans `usage::ProviderKey` and T-120 plans `adapters::ProviderId`;
  they should reuse this enum (same six ids, same serde form) rather than add a third.
- Run time accrues as wall-clock while at least one run is active (two overlapping runs count once). If the human wants
  per-session accounting (stricter), `RunClock` is the one place to change. Wall-clock differences are used, so a user
  moving the system time forward could add run time (stricter) but never remove it (the day only rolls forward).
- Limits apply to every `ProviderId` including gemini and glm; API-key limit sets are Phase 3, as the brief says.
- `BackendEvent` payloads are `serde_json::Value` because the typed snapshots belong to other briefs. The owning
  modules build the JSON; a typed layer can be added later without changing the event names.
- Integration tests under `tests/` cannot see `SimClock` unless `--features sim` is on, so `limits_public_api.rs` uses
  its own `Clock`. The unit tests use `SimClock`. T-125 needs `sim` enabled for its own test target (see follow-ups).
- `SessionPermit` holds an `Arc` to the limits state, so a permit stays valid and releases correctly even if every
  `ProviderLimits` handle is dropped first.
