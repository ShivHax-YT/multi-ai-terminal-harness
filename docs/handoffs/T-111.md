# HANDOFF T-111
## Summary
Core primitives for Phase 1. `clock`: `Clock` trait, `SystemClock` (the only reader of the OS clock; on macOS its monotonic
reading counts time spent suspended), `SimClock` (behind `cfg(any(test, feature = "sim"))`, with wall-clock jump helpers).
`events`: `BackendEvent` (six contract names, JSON snapshot payloads), `EventSink`, `NullSink`, `RecordingSink`.
`limits`: in-memory rule 1 enforcement (session permits, rolling 60-minute prompt window, turns per task, per-run daily
run time, idle/background/stale presence) with every limit read from `compliance::ceilings` and `min(user, ceiling)` as
the only combination. Round 2 closed the clock-tampering, accounting and presence bypasses found in review and by Codex.

## Open risks / questions
- Trusted time is anchored to the wall clock once, at the first call. If the wall clock is far wrong at that moment and
  corrected later, the day key stays off until restart; a saved later day is then kept by `load`, which is the fail-safe
  direction (stricter). On macOS the monotonic clock counts suspend time, so closing the laptop does not delay the day
  roll. On other platforms `SystemClock` uses `Instant`, which stops while suspended, so a long suspend would delay the
  roll there (stricter). A real clock-sync policy is a human decision if wanted. The 5-minute tolerance idea was not
  needed: the timeline never follows the wall clock after the anchor, so there is no per-call slack to accumulate.
- Integration requirements for T-112 and T-124/T-125 (also in the `tracker.rs` module docs):
  - Keep ONE `ProviderLimits` instance for the whole app (clone the handle); two instances start from zero.
  - Call `load()` with the persisted snapshot before the first admission after every start.
  - T-112 must store seconds (`RunDay.seconds`, already rounded up), not minutes, and decide whether turn counts carry a
    provider (`record_turn` now takes a provider for the pause check, but the persisted turn map is keyed by task id).
  - T-112 should snapshot periodically while a run is open, and persist before dispatching a prompt: `admit_prompt` only
    counts in memory, and a crash otherwise loses the live stretch of a run and the last prompts.
  - T-124/T-125 must poll `must_pause(provider)` while a run is active (an open run passing 480 minutes is otherwise only
    stopped at the next admission), and must couple every dispatch to a `SessionPermit`, an open `RunGuard`, a
    `record_turn` reservation and `admit_prompt`; no single check is sufficient.
  - The app must call `set_presence` at least every 5 minutes with the user's real state; a missing or stale report stops
    all automation.
- `Refusal` has a new `CeilingKind::PresenceUnknown`; the app's `IpcError` mapping should treat it as `rule_blocked` rule 1.
- Limits apply to every `ProviderId`, including gemini and glm; API-key limit sets are Phase 3.
- A `RunGuard` or `SessionPermit` dropped while the clock itself panics would abort during unwinding; the `Clock` contract is that it does not panic.
