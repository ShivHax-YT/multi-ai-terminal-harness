- **Codex top-level `error`**: the brief maps it to a fatal `error{stream_error}`. If Codex 0.162 also sends non-fatal `error` events (for example retry notices) in a successful run, the live capture will show an `error` event. The observed-capture rules in the brief do not fail on it (they check `unknown`, `result`, `rate_limited`, tokens), so a lead review of the first capture should look for it.
- **T-124 versus T-004 on `rate_limited`**: T-124's draft enters `rate_limited` "on a `rate_limited` event"; the T-004 brief (state machine row 7) enters it at invocation exit and counts once per invocation. The spec follows T-004. T-124 needs a one-line fix before it is approved.

No golden file is required for observed files (the test prints a NOTE); the lead may add `spike/normalize/expected/<cli>-observed.jsonl` after reviewing the capture.

The jq code avoids 1.7-only syntax (`if` without `else`, `abs`, `toarray`, `ltrimstr` on non-strings); jq 1.6 was not run, and number formatting such as `1.0` could differ between jq versions (no fixture uses such a literal). ### Spec decisions I had to make (flag for the lead)
- **`error{fatal:true}` in `spawning`** stays in `spawning` until the child ends (row 13). Reason: a fatal error is information, not
  an exit; the transition happens on the `exited` event, where `limit_seen` must still win (a Codex limit message emits
  `rate_limited` before its `error`).
- **Several `result` events**: the last one counts for the flags (as the brief says) and, my choice, for the turn settlement
  too (it replaces the reservation). Codex "1 per exec" is kept even if an exec emitted two `turn.completed`.
- **`result.turns` above the reservation** (a CLI that overshoots its own cap) is counted as reported. The scheduler cannot
  prevent a CLI overshoot, only shrink what the next dispatch gets; if you want a hard clamp, say so (open risk, rule 1).
- **After `cancel()`** (row 10) the adapter feeds no further event of that child to the function, not even its `exited` event,
  because the brief makes every event after a terminal state illegal. The turn reservation stays counted. T-124 needs this.
- **`cancel()` in `exited`/`killed`** is a legal no-op (row 16), since the method is documented idempotent.
- **`exited` event with neither code nor signal** after a successful `result` is not a clean exit (row 11, fail safe).
- `message`, `tool_call`, `tool_result` and `result` in `spawning` are illegal (they come after `session_started`).
- Spec row 6 still says "a watchdog kill that was not a `cancel()`" while row 10 sends the watchdog to `killed` (pre-existing
  wording, left alone); the new turn text lists "the watchdog" among the no-result cases either way.
