# HANDOFF T-116

## Summary

Replaced the lead's placeholder `plan/mod.rs` with the plan model: a strict one-document parser (duplicate keys at any
depth, invalid UTF-8, lone surrogates, trailing documents and any non-canonical or over-2^53-1 number are refused), an
RFC 8785 canonicalizer for the integer/string subset, the plan hash (`sha256(jcs(plan without approval))`, approval
removed from the parsed value), schema-exact shape validation and a port of every `spike/plan/check.jq` rule with its
rule number and message wording. `Plan::from_bytes` is the single parse: value, hash and typed model all come from it.
`check(plan, Mode::Pre | Mode::Scheduler)` returns `Vec<Violation { rule, message, task_id }>` (serializes to
`PlanViolation`). Pure module: no file, process, adapter or pty-view access. `plan/simulation.rs` is untouched.

## Open risks / questions

1. **Spike hash framing differs from JCS (needs a lead decision).** `spike/plan/hash.sh` pipes `jq -S -c` straight into `shasum`, so it hashes the canonical bytes plus a trailing newline. RFC 8785 and this brief define the hash over the canonical bytes alone. Result: the `approval.plan_hash` stored in `docs/spec/examples/plan-approved.json` (c16ef69c...) is `sha256(jcs + "\n")` and does not verify against this module's hash (dae6b286...); `plan-stale-approval.json` is unaffected in meaning. I kept the brief's definition, did not touch `docs/spec/**` or `spike/**`, and pinned the relationship in `plan::spike_hash_differs_only_by_a_trailing_newline`. Tests that need an approved plan rebind `approval.plan_hash` to the computed hash. Lead action: regenerate the example approvals (and fix `hash.sh`/`plan.md`'s "spike" line) in a T-005 follow-up, or tell me to switch the framing. The spike script keeps passing because it is untouched.
2. **Deviation: negative or fractional numbers are parse errors, not violations.** The brief says non-canonical numbers are rejected at parse time, so spike cases such as `turns: -1` or `1.5` yield `ParseError::NonCanonicalNumber` rather than a `rule 1:` violation line. Wrong types (`true`, `null`, string) and out-of-range values (over 1000000) are still rule 1 / rule 9 violations with the spike messages.
3. **Deviation: `Violation.message` has no `rule N:` prefix.** `Display` renders the spike's `rule N: message` line (tests assert on that). `task_id` is set when the finding is about one task.
4. **Non-object documents.** `Plan::from_bytes` accepts any single canonical-subset JSON value; a top-level array/string is reported by `check` as `rule 9: plan must be a JSON object` (matches the spike), and `Plan::model()` is `Err`. Callers must treat any non-empty `check` result, or `model().is_err()`, as a rejection.
5. **Simulation hash.** `plan/simulation.rs` (T-132/T-133 sample flow) has its own scope hash and approval token and was left exactly as is, including its public items and call sites. Folding that hash into the JCS hash is a later lead decision.
6. **Added limits, not in the brief:** documents over 4 MiB or nested deeper than 32 levels are refused (fail closed, bounded recursion).
7. `check-fast` runs only `cargo test --lib` for Rust; the integration tests in `tests/plan_*.rs` run under `make check` / `cargo test`. Core rule checks are duplicated as lib unit tests for that reason.
8. The editing tool used for this work rewrote some `\uXXXX` sequences in source files into literal characters; the affected tests build their escapes at run time (`esc()` / `format!` with a backslash argument) so they test what they claim to. Worth keeping in mind for future edits of those test files.
