## Design
1. **Request state.** `thinking -> plan_ready | rate_limited | error | cancelled`. One request in flight at a time. The
   lead is started through the session manager as a headless session of the chosen provider (`start_lead_request`
   takes `{lead, text}`; the backend picks `auth_mode` from `usable`, see Notes).
2. **Plan.** The lead's final output is parsed once by T-116's strict parser. A parse or checker failure is shown as
   violations, never executed. A valid plan is stored with `status: draft` and emits `plan_changed`.
3. **Edits.** `update_plan` applies one `PlanEdit` and returns a new hash; the approval is cleared (T-117 `invalidate`)
   and `needs_reapproval` is true when an earlier approval existed.
4. **Dispatch.** After `approve_plan` (T-117), the scheduler (T-125) dispatches one worker in its worktree (T-118). The
   worker's brief contains the task, owned files, acceptance and the HANDOFF.md instruction. Briefs are scanned for
   secrets before dispatch (rule-level check: a fixture with a fake key is refused).
5. **Verify.** When the worker exits, the verify run (T-129) executes; the status feeds `ReviewListItem.state`.
6. **Summary.** The lead gets one headless call with the task result, diff stats and test status, and must answer in
   at most `summary_budget_tokens` (default 200). Over budget: one retry is NOT allowed (rule 10 spirit: no loops); the
   summary is truncated at the last complete sentence within budget and flagged.
7. **Stop.** Any refusal or limit stops the pipeline at that step and shows the reason. Nothing retries automatically.

## Hard rules touched (docs/HARD_RULES.md) and the test that proves each
| Rule | How this task satisfies it | Test |
|---|---|---|
| 9 | No worker starts without a valid approval token | `cargo test -p harness-core lead::no_dispatch_without_approval` (pipeline run with the approval step skipped is refused) |
| 9 | Lead output cannot approve; `approve_plan` is not reachable from the lead module | `cargo test -p harness-core lead::no_approval_symbol` (greps `lead/**` for `approve`, `SigningKey`, `ApprovalToken::mint`) |
| 3 | Lead module has no PTY symbol or dependency | `make crate-boundary` and `cargo test -p harness-core lead::no_pty_symbols` |
| 1 | Lead run counts toward prompt and turn ceilings | `cargo test -p harness-core lead::counts_toward_ceilings` |
| 4 | Canary: planted fake credential files in a temp home are never opened by the app process during a full run | `cargo test -p harness-core --test canary_full_session` (plants `.claude/.credentials.json`, `.codex/auth.json`, `.claude.json` in a temp HOME; runs the full pipeline with fake CLIs; asserts zero `fs_guard` trace events for those paths and zero reads by the app) |
| 5 | No listening socket after app start; no `0.0.0.0` bind in source | `cargo test -p app --test no_listener` (starts the command layer, lists sockets via `lsof -nP -iTCP -sTCP:LISTEN` filtered to the app pid, expects none; greps `src-tauri/**/*.rs` for `TcpListener::bind` and `0.0.0.0`) |
| 2 | Lead and fake runs never set config-home variables | `cargo test -p harness-core lead::no_config_home` |
| 10 | Limit error in the lead run pauses the provider; no retry | `cargo test -p harness-core lead::limit_error_pauses_no_retry` |
