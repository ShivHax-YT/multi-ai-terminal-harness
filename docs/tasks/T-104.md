Status: proposed (the hands-off approval of 2026-10-25, commit deb08f4, was revoked by ShivHax-YT on 2026-10-26; only the human approves)

## Goal
Show one plan (tasks, roles, providers, owned files, acceptance, fallbacks, estimated usage against ceilings, violations) so the human can edit it and approve exactly what is shown. This screen is the only importer of the approval port. Approval is the only path to a running worker (rule 9).

## Design pre-flight (before code)
- **Screen goal:** Read what the lead planned, fix it if needed, and approve exactly what you read.
- **Primary action:** "Approve plan" with the first 8 characters of the hash (filled). It appears only when status is `draft` and `violations` is empty. Otherwise no button is filled, and the violation text explains why. `approved`, `running`, `done` and `superseded` are read-only.
- **Tokens:** `--card` (plan and task panels), `--primary` (approve only), `--warning` and `--destructive` with icon and text, `--muted-foreground` for estimates, mono for the plan hash, file paths and branch names.
- **Typography:** H1 plan title 24px semibold. Metadata 14px muted. Hash in mono 13px (per the README).
- **Wireframe, 1024 px** (task cards stacked):
```
+--------------------------------------------------+
| Plan: Add dark mode                 hash 3f9a2c1b|
| 3 tasks - draft                                  |
| [!] Blocked by rule 2: t2 lists one provider     |
|     twice in its fallbacks.                      |
| +----------------------------------------------+ |
| | t1  backend   <ProviderName>  2 files        | |
| |     fallbacks: <ProviderName>                | |
| +----------------------------------------------+ |
| [Edit provider] [Edit fallbacks] [Discard...]    |
| Estimate: <ProviderName> 14 prompts (ceiling 30/h)|
+--------------------------------------------------+
```
- **Wireframe, 1440 px** (task table, max 1200 px wide):
```
+----------+-------------------------------------------------------------+
| Sidebar  | Plan: Add dark mode                       hash 3f9a2c1b     |
| (240 px) | Task  Role      Provider      Files  Fallbacks               |
|          | t1    backend   <Provider>    2    <Provider>               |
|          | t2    frontend  <Provider>    3    -                        |
|          |                                   [Approve plan 3f9a2c1b]   |
+----------+-------------------------------------------------------------+
```
- **Signature motion:** Stagger on task rows, once, at most 300 ms, 40 ms step. The approve press uses shadcn's default press, because the T-101 wrappers have no spring primitive.
- **Inspiration technique borrowed:** Godly typographic scale on the plan header (24px title, 14px metadata, mono hash).
- **States:**
  - Loading: `LoadingSkeleton` while `get_plan` is pending (`plan_draft`).
  - Empty: "No plans yet. Ask the lead for one." linking to Lead. Test: discard the only plan in `plan_draft`, then expect the empty state.
  - Violations: `plan_violations` shows rule 1 (turns over 40), rule 2 (duplicate fallback) and a fallback outside the plan. No approve button.
  - Error: `ErrorAlert` (`errors`).
  - Stale hash: `failNext("approve_plan", plan_hash_mismatch)` shows "This plan changed. Review it again." and refetches.
  - Read-only: `running` shows the plan without edit controls.

## Behaviour
- Approve calls `useApproval().approve_plan({ plan_id, plan_hash })`, with the `plan_hash` from the `PlanView` on screen. Never on mount, on a `plan_changed` event, on Enter in a form, or from the palette. The button is not auto-focused.
- Every edit is one `update_plan` call with one `PlanEdit`. The returned `PlanView` replaces the cache. If `needs_reapproval` is true, show "Edited after approval. Approve again."
- Provider options: `MVP_PROVIDER_IDS`. Auth modes come from `ProviderStatus.auth_modes`. Gemini is API key only (rule 7).
- Adding a fallback provider that is outside the plan is an edit that voids approval (rule 9). Show "This needs a new approval" before the edit is sent.
- Discard uses `AlertDialog`. It is destructive and never the primary.
- Estimates show as `Meter` against `get_limits` ceilings (rule 1).
- Violation text comes from the backend. Show "Blocked by rule N" when a number is given.

- Schema: field names follow the merged `docs/spec/plan.schema.json`. The in-flight revision adds `format_version`, `lead.auth_mode` and `{provider, auth_mode}` fallbacks. If the merged schema lacks them, the contract type wins and the difference goes to the lead.
- Press spring: no press primitive exists in T-101's wrappers. Request to the lead only if a spring press is wanted.
- v1 approval is one click. A second confirmation step is not in the contract; request one only if wanted.
