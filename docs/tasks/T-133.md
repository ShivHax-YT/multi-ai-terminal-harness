## Goal

Establish what the native app can enforce before enabling repository execution. Implement independent, real Claude Code
and Codex installation verification and supported CLI status/onboarding without credential-store access. Enable worker
execution only after repository access, worktree creation, child processes, approvals, durable limits and recovery are
connected and independently verified. A browser demo or a passing refusal test does not count as native MVP acceptance.

The user's continuation authorizes targeted local implementation, testing and reviewable local changes. It explicitly
requires preserving current worktrees, staged/unstaged/untracked changes, and leaving operations unavailable where the
required boundary cannot safely be established. No push, merge, provider credential read or provider Keychain query is
authorized. No installer, purchase or subscription change is part of this task.

## Threat model and technical boundary

1. Paths, repository content, Git configuration and agent output are untrusted. Another process running as the same user
   may concurrently replace a component with a symlink, exchange real directories, or rename an already-open parent into
   a protected subtree. Protected destinations must remain untouched before refusal; detection or cleanup afterward is
   insufficient. Mode 0700 does not exclude another process with the same UID.
2. `O_NOFOLLOW_ANY` blocks symlink traversal on macOS. It does not prevent a real directory being renamed. A canonical
   pathname and a pinned descriptor are observations/references, not an authorization transaction spanning future I/O.
   Rechecking `F_GETPATH` is also a separate operation from creation, truncation, reading or writing.
3. The current `create_write` and `append` paths use `O_CREAT` before `verify_fd`. The current methods also return ordinary
   `File` handles; subsequent use cannot be re-authorized by the guard. These are unresolved limitations beyond the
   disabled directory-creation method. The per-operation deny snapshot does not constitute a permanent kernel label.
4. Git and arbitrary worker/test descendants issue their own syscalls. `git -C`, process `cwd`, worktree naming, and
   before/after pathname checks do not route those operations through Rust's guard. Repository hooks, filters,
   external diff/textconv, includes, alternates, submodules, replacement objects, inherited descriptors and environment
   are additional indirect access/execution surfaces. Sanitizing Git configuration is necessary but does not close the
   concurrent-rename boundary.
5. Rule 4 and T-114 explicitly distinguish the app's credential access from each official CLI's own supported login
   access. The harness may invoke a verified CLI's supported login/status flow; it must not inspect that CLI's store.
   This distinction does not authorize arbitrary agent tools to read other providers' credentials.
6. The precise blocker in the current architecture is absence of a kernel-enforced boundary mediating each relevant
   filesystem operation and descendant, while denying protected destinations and preserving permitted official CLI
   authentication. Ordinary same-UID POSIX pathname/descriptor APIs cannot atomically combine the app's custom
   path-deny policy with every future syscall. No amount of extra pre/post checks proves that guarantee.
7. A boundary may be supplied by a separately reviewed kernel-enforced broker/isolated execution environment that the
   attacker cannot rename into protected locations. It must include Git creation, workers and tests, plus explicit
   authentication handling. App Sandbox is expressly excluded by the existing deployment decision; a deprecated
   sandbox launcher or a provider's tool sandbox must not be assumed to satisfy all these obligations without
   independently testing them. Changing that architecture requires a concrete proposal, not a silent exception.

An attacker who can freely copy secrets into an allowed ordinary source file is outside any meaningful path-deny
confidentiality guarantee. This does not remove concurrent-rename regressions from scope or weaken the required
before-mutation checks. State explicitly whether a proposed mechanism protects current destinations, object identity,
or both; do not claim one proves the other.

## Implementation sequence

1. Preserve and record the initial Git state. Reproduce security regressions with fake protected homes only. Add
   deterministic real-directory replacement/rename and post-open-handle scenarios where appropriate; do not describe
   a symlink-only test as parent-rename coverage. Keep native repository import/worktree/worker dispatch unavailable
   unless the mechanism actually covers their indirect operations.
2. Verify current vendor interfaces against official documentation and installed versions. Separate discovery,
   provenance/signature verification, version, auth status and automation usability. Never invoke `--version`, `help`,
   `login`, `auth`, or any other verb on an unverified provider executable.
3. Use pinned vendor identity/provenance and bounded, sanitized subprocess execution. Reject unsigned look-alikes,
   wrong vendor signers, tampered binaries, untrusted paths and swapped executable identities before launch. Trust
   decisions must not come from arbitrary PATH entries, a local filename or unverified binary version output.
   A possible macOS native-only onboarding mechanism is `posix_spawn` with `POSIX_SPAWN_START_SUSPENDED`, followed by
   dynamic `SecCode` verification of the actual stopped child against a pinned vendor requirement before resume. A
   failure must kill/reap the stopped process without executing provider instructions. Verify the mechanism with
   executable-swap canaries; do not equate static pathname validation with the child's actual mapped image. Reject
   interpreter shims and constrain runtime injection/library loading. This protects against filesystem swaps, not
   another process sending `SIGCONT`, debugging, modifying the harness or tampering with process control; disclose
   those limitations. It creates a stopped process for validation and must not be described as creating no process.
4. Implement real status for supported verified Claude Code/Codex CLI interfaces. Report unavailable, unverified,
   signed out, signed in and usable separately. A signed-in CLI remains unusable for work while a boundary or another
   required safety primitive is missing. Do not infer sign-in from process success where documented structured output
   contradicts it. Bound output and timeout; avoid retaining account identifiers or token-bearing output.
5. Expose the official login flow for human interaction only after verification, with cancellation and result refresh.
   Keep Gemini API-key-only and other unsupported providers disabled. Mark remaining native fixtures and browser
   simulation honestly. No real prompt is needed for installation/auth status.
6. Only after all earlier gates pass, implement the actual repository-to-approval-to-worktree slice and connect
   durable quotas, session ownership, foreground/idle state, pacing/backoff, output, cancellation, review and recovery.
   Until then, do independent implementation/verification without launching an unsafe worker.

## Primary references for the bounded native onboarding mechanism

- [Apple XNU image activation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_exec.c):
  `POSIX_SPAWN_START_SUSPENDED` applies task suspension before the new process runs (current source lines 2068–2079).
- [Apple dynamic code validation](https://developer.apple.com/documentation/security/seccodecheckvalidity(_:_:_:)):
  validate the guest's dynamic code identity against an explicit requirement rather than re-resolving its pathname.
- [Apple guest lookup](https://developer.apple.com/documentation/security/seccodecopyguestwithattributes(_:_:_:_:)):
  obtain the kernel's guest code by the stopped child's PID and reject ambiguous/failed lookup.

These references support investigation of the narrow mechanism. They do not establish that arbitrary Git/worker
filesystem access is confined or that a same-UID adversary with process-control access is excluded by the OS.
