## Goal
Implement the Claude Code adapter from T-120 by running the unmodified `claude` binary headless. It starts one
invocation per task with the documented flags, parses the stream-json events into `NormalizedEvent`s by the mapping in
`spike/normalize/claude.jq`, resumes a session by ID for follow-ups, detects rate-limit and usage errors, and reads
auth status only from `claude auth status` by exit code. It never sets a config-home variable and never reads a
credential file.

## Design
1. **Invocation.** `claude -p <prompt> --output-format stream-json --verbose --permission-mode acceptEdits`, with
   `cwd` = the worktree. The permission mode is the value T-002 recorded as sufficient; `bypassPermissions` is never
   used (T-002 notes). `--max-turns` is passed with the task's remaining turn budget (at most 40) if the CLI's help
   lists it; the T-002 capture decides this.
2. **Resume.** A follow-up uses `claude -p --resume <session_id> <prompt> ...` in the same worktree. The session id comes
   from the `session_started` event of the previous invocation.
3. **Env.** Only the runner's allowlist (T-119). The adapter adds nothing. It never sets `CLAUDE_CONFIG_DIR`, and a
   test fails if that string appears in the adapter source.
4. **Parse and map.** Each JSONL line goes to the mapping table from `spike/normalize/claude.jq`. Unknown types become
   `unknown`. A `result` event must carry numeric token counts or the adapter emits `error` (never a silent zero).
5. **Limits.** A rate-limit or usage-exhausted event becomes `rate_limited { reset_at?, retry_after_s?, raw_kind }`
   with the shape from T-002's `EVENTS.md` (docs-sourced shapes are marked as such). The adapter never retries. The
   pacing gate (T-113) decides.
6. **Auth status.** `auth_status()` runs `claude auth status` (documented in T-001's preflight) and returns SignedIn
   or SignedOut by exit code only. Output is discarded, not stored or logged (rule 4). Timeout 10 s, unknown on timeout.
7. **Login.** `login_argv()` returns the CLI's documented login command (the exact argv comes from the T-002 capture;
   the brief does not invent it). The login runs in an interactive PTY owned by the app (T-123), not here.

## Hard rules touched (docs/HARD_RULES.md) and the test that proves each
| Rule | How this task satisfies it | Test |
|---|---|---|
| 3 | Headless `-p` only; no interactive invocation; no stdin write | `cargo test -p harness-core adapter_claude::args_are_headless` (asserts `-p` and `--output-format stream-json`, no `--continue` without `-p`) |
| 2 | No config-home variable set or named | `cargo test -p harness-core adapter_claude::no_config_home` (source grep for `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME`, `KIMI_CODE_HOME`) |
| 4 | Auth via exit code only; output discarded | `cargo test -p harness-core adapter_claude::auth_exit_code_only` (fixture command prints secret-like text; asserted absent from every returned value and log sink) |
| 4 | No credential file access | `cargo test -p harness-core adapter_claude::no_fs_access` (grep for `fs_guard`/`std::fs` in the adapter) |
| 10 | Rate-limit fixture lines map to `rate_limited` and never trigger a retry | `cargo test -p harness-core adapter_claude::rate_limit_maps_no_retry` |
| 1 | Every `result` carries numeric tokens; missing tokens is an error | `cargo test -p harness-core adapter_claude::result_tokens_numeric` |
| 3 | Rust mapping equals the T-004 jq mapping on every fixture | `cargo test -p harness-core adapter_claude::matches_jq_mapping` (compares with the expected output file generated from `spike/normalize/claude.jq`) |
