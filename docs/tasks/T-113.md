# T-113: Pacing, exponential backoff and the limit-error pause

Status: approved by ShivHax-YT, 2026-10-29 (chat: "Approve, start wave 1")

## Goal
Enforce rule 10 on every automated dispatch: at least 5 seconds between dispatches per provider, exponential backoff
starting at 60 seconds after any rate-limit error, and a pause after 3 consecutive limit errors that lasts until the
provider's reset time or until the user resumes it. The pacing gate is pure: it takes `now` from the clock and returns
a decision. It never sleeps and never starts a retry itself.

## Design
1. **Dispatch gap.** `PacingGate::check_dispatch(provider, now) -> Decision`. `Decision::Wait { until }` if fewer than
   5 s (the ceiling `min_dispatch_gap_s`, read from consts) have passed since the last admitted dispatch for that
   provider; otherwise `Decision::Go`. `record_dispatch(provider, now)` runs only after `Go` and the usage prompt is
   admitted.
2. **Backoff.** `record_limit_error(provider, now, retry_after: Option<Duration>)`. Attempt n waits
   `backoff_base_s * 2^(n-1)` = 60 s, 120 s, 240 s and so on, capped at the `backoff_base_s` upper bound of 3600 s
   from the contract. A `retry_after` from the CLI wins if it is longer. `attempt` resets only on a successful
   dispatch (`record_success`), not on a timer.
3. **Pause.** The third consecutive limit error sets `paused = true` with `paused_until` = the later of the last backoff
   end and the CLI-reported reset time when present. While paused, `check_dispatch` returns `Refused` with rule 10.
   The pause ends only at `paused_until` passing, or when `user_resume(provider)` is called. Resume is refused
   with rule 10 while the backoff window is still open (matching the contract's `resume_session` note).
4. **Rate limits are not retried in place.** The gate has no retry loop and no timer. The scheduler (T-125) asks
   "may I dispatch now?" on each tick. A limit error ends the current attempt and records state.
5. **No cross-provider effect.** A limit error on `claude` never changes state for `codex`. Failover is a scheduler
   decision (T-125), not a pacing one.
6. **Persistence.** All state goes through T-112's `save_pacing` / `load_pacing`. A restart reloads state; it does not
   clear a pause.

## Hard rules touched (docs/HARD_RULES.md) and the test that proves each
| Rule | How this task satisfies it | Test |
|---|---|---|
| 10 | At least 5 s between dispatches per provider | `cargo test -p harness-core pacing::min_gap_5s` (dispatch at t and t+4.9 s refused, t+5 s allowed) |
| 10 | Backoff 60 s, 120 s, 240 s; capped; CLI retry-after honoured | `cargo test -p harness-core pacing::backoff_sequence` |
| 10 | Pause after 3 consecutive limit errors; ends at reset time or on user resume | `cargo test -p harness-core pacing::third_error_pauses`, `pacing::pause_ends_at_reset`, `pacing::resume_refused_during_backoff` |
| 10 | Pause survives restart | `cargo test -p harness-core pacing::pause_survives_restart` |
| 10 | A limit error never causes a retry on the same provider | `cargo test -p harness-core pacing::limit_error_no_retry` (the gate emits no dispatch decision inside the backoff window) |
| 2 | A limit error on one provider never changes another provider's state | `cargo test -p harness-core pacing::limit_error_isolated_per_provider` |
