## Goal
Build the `pty-view` crate: spawn PTYs for three purposes only: (1) a read-only view of a worker's output, (2) a
take-over terminal where an interactive CLI runs in the worktree and only human keystrokes drive it, (3) the CLI's own
login. Two types enforce rule 3 in the compiler: `ViewPty` has no write method at all, and `InteractivePty` has the
write method, constructible only through the take-over and login constructors. Automation never gets a write path.

## Design
1. **Dependency.** `portable-pty`, pinned to a version verified to build on macOS in a spike (ADR 0001). The pin is a
   lead decision in `Cargo.toml`. This crate depends on nothing from `harness-core`.
2. **ViewPty.** `ViewPty::spawn_mirror(spec)` opens a PTY and runs a read-only viewer child: `tail -n +1 -F -- <path>`
   on an app-owned transcript file (the runner's raw stdout tee, written by the app under app data). `ViewPty` exposes
   `read_chunks()` and `resize()` only. No `write`, no `send`, no `Write` trait impl (compile-fail doctest).
3. **InteractivePty.** `InteractivePty::start_takeover(spec)` runs the provider's interactive CLI in the worktree with the
   runner's env allowlist. `InteractivePty::start_login(spec)` runs the adapter's `login_argv()`. Both are the only
   constructors. `write(&mut self, bytes: &[u8]) -> Result<()>` exists only here. Bytes are at most 4 KiB per call.
4. **Output ring.** Each PTY keeps a bounded scrollback ring (cap: see Notes) with `seq` numbers. `attach` returns
   the ring and the current `seq`. Output is never written to disk or logs (rule 4 in T-106's terms).
5. **Child cleanup.** Dropping either PTY kills its process group (SIGTERM, then SIGKILL after 2 s). Same pattern as
   T-119. Unsafe code needs `// SAFETY:` and a test.
6. **No input from the mirror.** The viewer child is `tail`, which ignores input. Even so, `ViewPty` has no write path, so
   keystrokes typed in view mode are never forwarded.
7. **Crate isolation.** No module in this crate names `harness_core`, `scheduler`, or `lead` (the boundary scan would
   flag `pty_write` in scanned paths; this crate is outside those dirs but the rule still applies in spirit).

## Notes / open questions
- **BLOCKING, human decision: PTY design (rule 3).** Option A (recommended, used here): the worker's PTY is a read-only
  mirror of its output; take-over starts an interactive CLI in the same worktree that only human keystrokes drive; the
  automated run never receives PTY input. Option B (rejected): take-over writes into the headless child's stdin, which
  breaks the JSON protocol and makes the scheduler's child reachable from the keyboard path. The human must approve A.
  T-106's screen brief has the same blocker.
- **Decision: take-over counting.** A take-over interactive CLI counts toward the 2-concurrent-session ceiling (the
  conservative default). The human may decide otherwise, but the ceiling is not changed by this brief.
- **Decision: scrollback cap.** Proposed 256 KiB per session. The contract does not state a cap (T-106 asks). The lead
  confirms.
- **Contract:** `pty_write.data` is UTF-8 text per T-106's assumption. The lead confirms; the bytes path is the same.
- **Resolved 2026-10-25:** ShivHax-YT approved Option A. Take-over counts toward the 2-concurrent-session ceiling.
  The lead confirms the 256 KiB scrollback cap and that `pty_write.data` is UTF-8 text.
