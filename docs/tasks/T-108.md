## Goal
Show each provider's estimated usage against the compiled ceilings and the user's stricter limits, its pacing and pause state, and, for API-key providers, spend against caps. Counters belong to the provider on this machine. Nothing on this screen resets them (rule 2).

## Design pre-flight (before code)
- **Screen goal:** See how close each provider is to a limit, and why it is waiting.
- **Primary action:** "Resume <provider>" (filled, at least 44 px tall: `min-h-11`) for the first provider in list order whose `pacing.paused` is true (after three limit errors, rule 10). Any other paused provider's Resume is outline. Otherwise no filled button, because the screen is read-only.
- **Tokens:** `--card` meter panels. `Meter` shows warning at 80% (icon and "80% of limit") and destructive at 100% ("At limit"). `--muted-foreground` captions. Numbers in Inter with tabular figures. `--warning` for pause text. Copy lines at most 65ch.
- **Wireframe, 1024 px:**
```
+--------------------------------------------------+
| Usage                                            |
| Estimates. Counters don't reset when you sign    |
| out or switch accounts.                          |
| +----------------------------------------------+ |
| | <ProviderName>  subscription                 | |
| | Sessions       1 of 2                        | |
| | Prompts/hour   12 of 30                      | |
| | Turns (t1)     18 of 40                      | |
| | Run minutes    95 of 480 today              | |
| | Next dispatch  in 0:04                       | |
| +----------------------------------------------+ |
+--------------------------------------------------+
```
- **Wireframe, 1440 px** (two cards side by side: subscription and API key):
```
+----------+-----------------------------------------------------------+
| Sidebar  | Usage                                                     |
| (240 px) | +------------------------+ +-------------------------+   |
|          | | <ProviderName>         | | <ProviderName> API key  |   |
|          | | Sessions    1 of 2     | | Spend today $3 of $25   |   |
|          | | Prompts/hr  12 of 30   | | Caps $25/day, $100/week |   |
|          | +------------------------+ +-------------------------+   |
+----------+-----------------------------------------------------------+
```
- **Signature motion:** Stagger on provider cards, once, at most 300 ms in total, 40 ms step. Meter fills do not animate (the T-101 `Meter` is static: it sets the width with no transition).
- **Inspiration technique borrowed:** Webflow stat card: a small label above a large value. No count-up animation (the fake-stat number ticker is rejected).
- **States:**
  - Loading: `LoadingSkeleton` while `get_usage` is pending (`ready`).
  - Empty: "No usage yet. Counters start once a provider is signed in." (`fresh`).
  - Error: `ErrorAlert` (`errors`).
  - Rate limited: `Countdown` to the backoff end, "Paused after 3 limit errors", Resume shown (`rate_limited`).
  - User idle: "Paused: you were away for 30 minutes" (`ready` with `setUserIdle(40)`).
  - Spend at cap: "Paused at your daily cap. Raise it in Settings." with a link to Settings (`api_key`, then `emit('usage_changed', ...)` with spend at cap).

## Behaviour
- Each meter shows `current`, `limit` (the user's stricter value) and `ceiling`. When the limit differs from the ceiling, say "Your limit".
- Idle: show `user_idle_minutes` against `idle_pause_minutes`. Show "App in background" when `app_in_background` is true.
- Every token and spend figure carries an "estimate" label when `is_estimate` is true.
- API key: caps are always shown in full. Never render "unlimited", and never an empty cap.
- No reset, clear or undo control anywhere on this screen.
- Resume calls `resume_provider`. The backend decides whether it is allowed. Do not hide the countdown.
- Refresh only from `usage_changed` events. No polling loop. Do not auto-retry on `rate_limited` or `rule_blocked` (rule 10).
