# T-008: Runner follow-up: separate stderr capture for live runs

Status: approved by ShivHax-YT on 2026-10-25 (hands-off authorization; lead-approved)
Phase: 0   Model hint: sonnet
Depends on: T-001 merged   Runs: alone (owns spike/lib); T-002 and T-003 adopt it afterwards

## Goal
The T-001 runner writes a child's stdout and stderr to one outfile, so T-002 and T-003 have to guess which lines are
events (a line starting with `{` is treated as stdout). Codex's review of T-003 rated that a bug: stderr JSON becomes
an event, and stdout text is lost. Add an optional, separate stderr file to the live and status entry points without
weakening any existing guarantee.

## Design
- New entry point `spike_run_live_split <seconds> <outfile> <errfile> <cmd> [args...]`, the same as `spike_run_live`
  except that stdout goes to `<outfile>` and stderr goes to `<errfile>`. The existing `spike_run_live` keeps its exact
  current behaviour and signature.
- `<errfile>` gets exactly the outfile policy: O_NOFOLLOW|O_APPEND, mode 0600, the same refusal of symlinks, hard links,
  non-regular files and paths outside the allowed roots, and opened by the same helper before exec.
- The live gate, default-deny tool policy, verified-copy rule, env allowlist, process-group kill, signal handling and
  watchdog all stay identical. The split adds no new way to run a command.
- `<outfile>` and `<errfile>` must differ after resolution; reject an identical path.
