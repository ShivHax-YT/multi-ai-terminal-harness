# T-114: File-access layer, credential denylist and the trace hook

Status: draft
Phase: 1   Model hint: sonnet
Depends on: T-101 merged   Runs: wave 1, parallel with T-111 and T-116

## Goal
Make the file-access layer the only way app code opens a file outside the repo or a worktree, and make the denylist of
CLI home directories and Keychain service names a single compiled-in data file. Every open goes through one function
that checks the denylist first and records a trace event. The credential canary (rule 4) later reads that trace to
prove the app process never opened a planted credential file.

## Design
1. **Denylist data.** `compliance/denylist.toml` lists `home_dirs` (`.claude`, `.claude.json`, `.codex`, `.grok`,
   `.kimi-code`, `.gemini`), `keychain_services` (the CLI-owned service names, listed as data only), and
   `allowed_exceptions` (empty in Phase 1). It is embedded with `include_str!` and parsed once at startup. Denylist
   paths are matched against canonicalized absolute paths after `$HOME` expansion done by the caller, not here.
2. **One door.** `fs_guard::open_read(path) -> Result<File, GuardError>`, `read_to_string`, `read_dir`, `metadata`,
   and `create_write` (for app-owned paths only). Each call: canonicalize, check the denylist (deny wins over any
   allow rule), check the root is one of the registered roots (repo, worktrees, app data dir), then open and record
   a `TraceEvent { path_hash, op, outcome, at }`. The trace stores a hash of the path, not the path, so the trace
   itself holds no sensitive path.
3. **Deny by default.** A path outside every registered root is refused even if not on the denylist.
4. **Exception for binaries.** `fs_guard::exec_resolve(path)` allows resolving and returning a CLI binary path for the
   binary verifier (T-115) only. It does not open the file contents. The verifier receives a path, never a handle to
   the directory.
5. **Trace hook.** `TraceSink` is a trait. The app installs a sink in production. Tests install a recording sink and
   read it back. The sink is process-wide only through an explicit `install`.
6. **Symlinks.** Canonicalization resolves symlinks before the check, so a link from a worktree into `~/.claude` is
   denied.

## Hard rules touched (docs/HARD_RULES.md) and the test that proves each
| Rule | How this task satisfies it | Test |
|---|---|---|
| 4 | Denylist paths refused; deny wins over allow; outside-root paths refused | `cargo test -p harness-core fs_guard::denylist_refuses_cli_homes`, `fs_guard::deny_beats_allow`, `fs_guard::outside_roots_refused` |
| 4 | Symlink into a denied home is refused | `cargo test -p harness-core fs_guard::symlink_into_denied_refused` (temp dir with a link to a fake `.claude`) |
| 4 | Credential canary (unit form): planted fake credential files are never opened through the layer | `cargo test -p harness-core fs_guard::canary_planted_files_never_opened` (plants `.claude/.credentials.json`, `.codex/auth.json` in a temp home; asserts zero trace events with those paths) |
| 4 | Keychain service names in the denylist file only | `cargo test -p harness-core fs_guard::keychain_names_only_in_denylist` (greps `src-tauri/**/*.rs` for the service names; must find none) |
| 4 | No raw `std::fs` open of app-supplied paths outside this module | `cargo test -p harness-core fs_guard::no_raw_fs_outside_module` (greps the crate source for `File::open`, `fs::read`, `read_to_string` outside `fs_guard/`) |
| 6 | Verifier may resolve and execute a binary path, never read its directory | `cargo test -p harness-core fs_guard::sibling_file_unreadable` (sibling canary next to a fake binary stays unopened) |

## Notes / open questions
- The denylist is the Phase 1 list only. Windows credential paths are Phase 5.
- The layer does not cover the child CLIs' own file access; that is by design (each CLI reads its own login).
- The full-session canary (app process runs a fake headless session and the trace is checked) is in T-130, once the
  runner and adapters exist.
- Rule 4 names `~/.kimi-code` while the compliance scan also lists `.kimi`. Keep both in the denylist; the human may
  confirm the exact directory name for Kimi before Phase 3.
