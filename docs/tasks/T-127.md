## Goal
Replace the T-101 stubs for `get_settings`, `update_settings`, `get_limits`, `set_api_key`, `update_spend_caps` and
`remove_api_key`. Settings can only tighten the limits: any value looser than the compiled ceiling is refused. Spend
caps are required, finite and bounded, and no config path accepts "unlimited" (rule 11). Storing an API key in the
Keychain is a Phase 3 feature, so in Phase 1 the key path validates the caps and then returns `not_implemented` without
storing or echoing the key.

## Design
1. **Settings store.** One JSON file in the app data directory, written atomically (temp file in the same folder, then
   rename). Path supplied by the caller. Reads and writes go through `fs_guard`. A corrupt file falls back to the
   defaults for limits and never raises a limit above the ceiling.
2. **Limits.** `Settings.limits` is `Record<LimitKey, number>`. `update_settings` validates each key against
   `get_limits`: for `lower` rules the value must be in `[bound, ceiling]`; for `higher` rules in `[ceiling, bound]`.
   Out of range returns `rule_blocked` with rule 1 (or 10 for the pacing keys). Non-integers are `invalid_input`.
3. **Summary budget.** `summary_budget_tokens` accepts positive integers up to 1000000 (plan.md). The contract has no
   range yet (T-109 asks the lead); the bound is taken from plan.md and recorded as a request.
4. **Caps (rule 11).** `SpendCaps::new(daily, weekly, max)` requires finite values, each greater than 0 and at most
   `spend_cap_max` (`{daily_usd: 500, weekly_usd: 2000}` placeholder until the human sets it), and `weekly >= daily`.
   There is no constructor, default or `Option` that yields an unlimited cap. Missing caps, zero, negative, `NaN`,
   `Infinity` and out-of-range values are `invalid_input`.
5. **API keys (Phase 1 stub).** `set_api_key` validates the caps first (missing caps is `rule_blocked` 11), then returns
   `not_implemented` without storing or echoing the key. `update_spend_caps` validates and stores the caps in the
   settings file (caps are not secrets). `remove_api_key` returns `not_implemented`. The key value is never logged,
   never placed in an error message, and never returned.
6. **Gemini.** Caps and key form apply to `gemini` only as API key mode. The validation has no sign-in path (rule 7).
7. **Idempotence.** Refused updates do not change the stored file (write only after validation).

## Hard rules touched (docs/HARD_RULES.md) and the test that proves each
| Rule | How this task satisfies it | Test |
|---|---|---|
| 11 | Config with no cap, zero, `Infinity`, above max, or weekly below daily fails validation | `cargo test -p harness-core settings::caps_required_finite_bounded` (table of cases) |
| 11 | No unlimited value exists in any type or config path | `cargo test -p harness-core settings::no_unlimited_value` (greps the module for `Option<SpendCaps>` in settings, `f64::INFINITY`, `unlimited`) |
| 11 | `set_api_key` without valid caps is refused and nothing is stored | `cargo test -p app settings::set_key_needs_caps` |
| 11 | The key is never echoed or logged | `cargo test -p app settings::key_never_echoed` (fixture key string absent from every return value and error) |
| 1 | Limits looser than the ceiling refused; stricter accepted | `cargo test -p harness-core settings::limits_within_bounds` (uses `get_limits` as the source) |
| 10 | Pacing keys validated against their bounds | `cargo test -p harness-core settings::pacing_keys_bounded` |
| 2 | Settings has no key that changes config home, profile or account | `cargo test -p harness-core settings::no_profile_keys` (schema of `Settings` has only the contract's fields) |
