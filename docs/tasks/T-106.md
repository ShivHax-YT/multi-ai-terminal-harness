## Goal
Show one session's raw PTY bytes in xterm.js. Input is read-only by default. Keystrokes reach the PTY only when a human has take-over on and the key came from a real keyboard or paste event. The lead, the scheduler and every automated path never reach this write path (rule 3).

## Design pre-flight (before code)
- **Screen goal:** Watch the worker's terminal. Take over only when you mean to.
- **Primary action:** "Take over" is outline, because an accidental take-over is the main risk. While take-over is on, "Return control" is the only filled button (at least 44 px tall: `min-h-11`; it calls `set_takeover` with false, and the session stays paused until Resume). Login sessions have no filled button.
- **Tokens:** `--terminal-bg` and `--terminal-fg` only (dark in both themes), mono 13px at 1.5 line height. `--warning` banner with icon and text. `--muted-foreground` status line. `--ring` for focus.
- **Wireframe, 1024 px:**
```
+--------------------------------------------------+
| worker  <ProviderName>  t1  running  [Take over] |
+--------------------------------------------------+
| <worker output>   (xterm, #0E0E11 background)    |
| ...                                              |
|                                                  |
+--------------------------------------------------+
```
  With take-over on:
```
| [!] Take-over on. Keystrokes go to this session. |
|                                 [Return control] |
```
- **Wireframe, 1440 px** (terminal fills the content column, max 1200 px):
```
+----------+-----------------------------------------------------------+
| Sidebar  | worker  <ProviderName>  t1  running      [Take over]      |
| (240 px) | +-------------------------------------------------------+ |
|          | | <worker output>   (xterm)                             | |
|          | +-------------------------------------------------------+ |
+----------+-----------------------------------------------------------+
```
- **Signature motion:** none. Terminal output is never animated. The take-over banner appears instantly.
- **Inspiration technique borrowed:** Godly: one thin status line above the content, with no extra chrome.
- **States:**
  - Loading: `LoadingSkeleton` "Connecting to the session" until `attach_terminal` resolves (`running`).
  - Empty: "No output yet." when scrollback is empty (`fresh`, login session).
  - Error: `ErrorAlert` when attach fails (`errors`). A refused keystroke shows "Blocked by rule 3" (`running`, take-over off, forced write).
  - Ended: "Session ended." read-only when the state is `exited` or `killed`.

## Behaviour
1. **Output.** Decode `terminal_output.data_b64` to bytes and write them to xterm in `seq` order. A gap in `seq` triggers `attach_terminal` again, which replaces the buffer. Parse nothing from the screen.
2. **Input gate.** One module, `input-gate.ts`, is the only code that calls `usePtyInput().pty_write`. It forwards data only when (a) the latest `SessionView.takeover` is true and (b) a trusted `keydown` or `paste` on the terminal element happened in the same turn (a capture-phase flag, cleared on the next macrotask). xterm also emits `onData` for its own replies, such as cursor-position reports answering output escape codes. Those are dropped.
3. Binary input (`onBinary`) is dropped. Paste is split into chunks of at most 4 KiB.
4. **Links.** No `WebLinksAddon`. The xterm link handler's `activate` is a no-op. OSC 52 stays off. Window title changes are not shown.
5. **No retention.** Chunks never go to localStorage, sessionStorage, console, logs or the query cache beyond the live buffer.
6. `resize_terminal` on fit. Take-over and Return control call `set_takeover`. A `rule_blocked` refusal is displayed, not retried.
7. **Keyboard during take-over.** With take-over on and the terminal focused, every Ctrl combination and Esc go to the PTY (Ctrl+K kill line, Ctrl+B tmux prefix, Ctrl+digit). App shortcuts use ⌘ only on macOS (the lead's shell and sidebar fix), so ⌘K still opens the palette.

## Notes / open questions
- **BLOCKING, decide before this brief starts:** what does a worker's PTY run? ARCHITECTURE.md says the PTY is view and take-over only, and the headless adapters emit JSONL. Option A (recommended): the PTY is a read-only mirror of the worker's output. Take-over starts an interactive CLI in the same worktree that only human keystrokes drive, and the automated run never receives PTY input. Option B: take-over writes into the headless child's stdin, which would break the JSON protocol. The lead or the human chooses. The gate in this brief works with both.
- **`pty_write` data type:** the contract does not say whether `data` is a UTF-8 string or base64. This brief assumes a UTF-8 string from `onData`. Confirm.
- **Scrollback:** `attach_terminal` returns `scrollback_b64` with no size limit stated. Confirm the cap.
- **Testing:** xterm needs layout. Terminal tests mock `@xterm/xterm` with a fake that records writes and emits `onData` on demand. Real rendering is a human check.
- **Ceilings:** take-over does not change any ceiling. Automation stays paused while take-over is on (contract: `takeover` pause reason).
